# Revisão do FluxoOS — 05/11/2026

A aplicação compila, empacota e inicia localmente. A estrutura controller → service → repository atende ao projeto; os problemas encontrados não exigem voltar à arquitetura hexagonal.

Atualização após a revisão: o item 1 foi corrigido com `StrictHttpFirewall`, `setAllowSemicolon(false)` e aplicação do firewall antes do filtro de autenticação. URLs com ponto e vírgula literal ou codificado agora retornam 400 no servidor real. O build final passou com 17 testes. Os demais achados continuam pendentes; as evidências abaixo registram o comportamento anterior à correção.

## Escopo e evidências

- Revisados backend Java, mapeamentos JPA, DTOs, migrações, módulos JavaScript, estrutura e estilos da interface, configuração YAML, scripts, Compose, workflow e testes.
- Executado novamente `mvnw verify`: **15 testes passaram**, sem falhas, e o JAR foi empacotado.
- Iniciado o servidor Tomcat real com configuração YAML, H2 em memória e carga demonstrativa, em porta aleatória na própria máquina. Página inicial respondeu 200; login e consultas foram exercitados por HTTP.
- Os testes exploratórios usaram somente dados de demonstração isolados. O banco em `data/` não foi alterado.
- As provas estão em `target/revisao/RevisaoProbe.java` e `target/revisao/resultado.log`; o resultado do build está em `target/revisao/maven-verify.log`. Esses arquivos são temporários e desaparecem com `clean`.
- Não foram executados testes contra PostgreSQL, testes de carga, auditoria de CVEs das dependências nem validação visual/interativa em navegador. A análise estática da interface não substitui testes em celular.
- O código funcional não foi modificado nesta revisão.

## Problemas encontrados

### 1. Crítico — consultas protegidas podem ser acessadas sem autenticação

Origem: [ProtecaoHttp.java](../src/main/java/br/com/fluxoos/config/ProtecaoHttp.java), linha 26.

O filtro verifica `getRequestURI().startsWith("/api/")`. O servidor e o roteamento Spring aceitam parâmetros de caminho com ponto e vírgula. Com isso, uma requisição pode deixar de entrar na verificação do filtro e ainda alcançar o mesmo controller.

Resultados confirmados no servidor real, sem cookie e sem login:

| Requisição | Resultado |
| --- | --- |
| `GET /api/usuarios` | 401 |
| `GET /api;revisao/usuarios` | 200, dados da equipe |
| `GET /api;revisao/ordens` | 200, ordens de serviço |
| `GET /api;revisao/materiais` | 200, dados do estoque |
| `GET /api;revisao/movimentos` | 200, histórico do estoque |

Isso permite leitura de dados internos sem autenticação. Não foi demonstrada alteração não autorizada de estoque ou contas; os services de escrita ainda verificam o ator. Entretanto, o controle central da API está vulnerável e deve ser corrigido antes da publicação.

A correção deve alinhar o tratamento do caminho ao roteamento, rejeitar URLs ambíguas e proteger a API por padrão. Uma configuração pequena de Spring Security com firewall de requisições é uma opção; ela é compatível com a estrutura simples atual. Acrescentar testes de regressão com servidor real para ponto e vírgula, caminhos codificados, contexto da aplicação e rotas de assinatura. A documentação oficial explica os riscos dos parâmetros de caminho em controles de acesso: [HttpFirewall](https://docs.spring.io/spring-security/reference/7.0/servlet/exploits/firewall.html).

### 2. Alto — reativar uma conta restaura sessões antigas

Origem: [UsuarioService.java](../src/main/java/br/com/fluxoos/service/UsuarioService.java), linha 40; [SessaoService.java](../src/main/java/br/com/fluxoos/service/SessaoService.java), linha 53.

`alterarStatus` altera apenas o campo `ativo`. A sessão continua armazenada e não é revogada. Confirmado: o mesmo cookie recebe 401 depois da desativação e volta a receber 200 depois da reativação, sem novo login.

Revogar todas as sessões quando a conta é desativada. Reativar deve permitir um novo login sem recuperar a validade dos tokens antigos. Adicionar teste específico de desativação seguida de reativação; o teste atual verifica somente o período de desativação.

### 3. Alto para operação contínua — sessões e limites de login crescem sem limpeza

Origem: [SessoesEmMemoria.java](../src/main/java/br/com/fluxoos/repository/SessoesEmMemoria.java), linha 13; [LimitadorTentativas.java](../src/main/java/br/com/fluxoos/seguranca/LimitadorTentativas.java), linha 11.

As sessões expiradas/revogadas permanecem no mapa. Nomes de usuário e IPs também permanecem nos mapas do limitador, mesmo após a janela de bloqueio. Não há expiração das entradas, capacidade máxima nem tarefa de limpeza. Nomes inexistentes também criam entradas, o que permite crescimento induzido por requisições de login. A magnitude do consumo de memória não foi medida em teste de carga.

Adicionar expiração, limite de capacidade e limpeza. Para uma implantação inicial, uma única instância é suficiente; memória local implica novo login após reinício. Para múltiplas instâncias, será necessário compartilhar sessões e limites ou adotar outra solução que mantenha essas garantias.

### 4. Médio — erros de entrada são reportados como falhas internas

Origem: [TratamentoErros.java](../src/main/java/br/com/fluxoos/controller/TratamentoErros.java), linha 37.

Confirmado com sessão válida:

| Requisição | Atual | Esperado |
| --- | --- | --- |
| `GET /api/ordens/abc` | 500 | 400 |
| `DELETE /api/materiais` | 500 | 405 |

O handler genérico captura exceções de conversão de parâmetros e métodos HTTP não suportados. Tratar os casos conhecidos preservando os códigos apropriados e testar também 404/406/415. O log de erro inesperado registra apenas o nome da classe; melhorar o diagnóstico com contexto e stack trace sanitizados, sem registrar senha, cookies, CSRF ou imagem de assinatura.

### 5. Médio — consultas e interface carregam toda a base

Origem: [OrdemServicoService.java](../src/main/java/br/com/fluxoos/service/OrdemServicoService.java), linha 27; [EstoqueService.java](../src/main/java/br/com/fluxoos/service/EstoqueService.java); [app.js](../src/main/resources/static/js/app.js), função `atualizar`.

As listagens de ordens, materiais, usuários, movimentos e eventos não têm paginação. `atualizar` busca as quatro coleções principais após várias operações. A listagem de ordens carrega entidades completas, incluindo a coluna de assinatura, e acessa coleções de itens por ordem; esse caminho favorece consultas adicionais por registro. O DTO evita enviar a imagem na listagem, mas não evita sua leitura do banco.

Usar paginação e filtros no servidor, uma consulta resumida para listar OS sem assinatura/itens completos e consultas de detalhe quando necessário. Atualizar apenas os dados afetados na interface. São melhorias de crescimento; não há medição que demonstre lentidão na base pequena atual.

### 6. Condição de implantação — HTTPS no proxy precisa de configuração explícita

Origem: [ProtecaoHttp.java](../src/main/java/br/com/fluxoos/config/ProtecaoHttp.java), linha 36; [application.yml](../src/main/resources/application.yml).

O filtro compara `Origin` ao protocolo, host e porta percebidos pelo backend. Se o usuário acessa HTTPS e o proxy encaminha HTTP, a comparação pode falhar. Na configuração padrão, uma requisição simulando esse cenário retornou 403, mesmo com cabeçalhos `X-Forwarded-*`.

Configurar o tratamento dos cabeçalhos encaminhados conforme o proxy e restringir sua confiança ao proxy real. Verificar também o endereço IP recebido pelo limitador: sem o tratamento adequado, vários usuários podem ser contados como o mesmo IP. As opções são descritas na [documentação Spring Boot 3.5](https://docs.spring.io/spring-boot/3.5/how-to/webserver.html#howto.webserver.use-behind-a-proxy-server). Não confiar indiscriminadamente em cabeçalhos enviados pelo cliente.

## Funcionalidades ainda ausentes ou limitadas

Estes pontos precisam de decisão de produto; nem todos impedem um piloto:

- Recuperação de acesso e redefinição administrativa de senha. Hoje só é possível trocar a própria senha conhecendo a atual. Também não há troca obrigatória da senha inicial.
- Correção/estorno de consumo vinculado à OS. A devolução manual aumenta o estoque, mas não corrige os itens da ordem nem referencia obrigatoriamente o consumo original. O mesmo material não pode ser adicionado novamente à mesma OS.
- Edição de dados de materiais e contas/perfis existentes; edição, cancelamento ou reabertura de ordens conforme regras a definir.
- Quantidades fracionárias, caso unidades como metro ou quilograma precisem de frações; o saldo atual é inteiro.
- Filtros e paginação de auditoria administrativa. Eventos de criação/desativação de contas são gravados, mas a tela de segurança consulta apenas os tipos do enum de segurança. `ACESSO_NEGADO` está declarado no enum e não tem emissão implementada nos fluxos revisados.
- Definição de visibilidade por unidade/solicitante, se necessária. Atualmente usuários autenticados consultam todas as OS e assinaturas, conforme o README. Isso é a regra atual, não uma segregação por organização.
- O perfil `SOLICITANTE` apenas consulta. Se o solicitante precisar abrir seus chamados, falta esse fluxo e sua autorização no servidor.
- Relatórios/exportação, anexos, notificações e modo offline não estão implementados. Acrescentar somente conforme necessidade.

## Melhorias que mantêm o código simples

- Dividir `OperacaoController` em controllers de OS, materiais e usuários, caso o arquivo continue crescendo.
- Organizar os DTOs de `Contratos` por assunto ou em arquivos separados quando facilitar a navegação. Não é necessário criar interfaces para cada service ou mapeadores genéricos.
- Padronizar imports e formatação. Há imports com `*` e imports redundantes do próprio pacote.
- Centralizar as durações de sessão e cookie: as oito horas aparecem na configuração de sessão e no controller. Hoje coincidem, mas uma alteração em um único lugar pode causar divergência.
- Tratar a sessão entre abas: o cookie é compartilhado, enquanto CSRF fica no `sessionStorage`. Um novo login em outra aba pode deixar a anterior com um CSRF que não corresponde ao novo cookie.
- No frontend, separar o sucesso da gravação da atualização da tela. Há formulários em que a gravação pode ser confirmada no banco e uma falha posterior em `atualizar` aparece como erro de envio; sem idempotência, repetir pode criar outra OS. Acrescentar recuperação desse estado e testes.
- Rever o script `executar.ps1`: ele decide solicitar a senha inicial pela existência de um arquivo H2 fixo. Um arquivo criado antes de um bootstrap malsucedido ou uma URL de banco diferente pode tornar essa decisão incorreta.
- Medir o login sob concorrência: `autenticar` é `synchronized`, então todos os logins compartilham uma fila durante PBKDF2 e acesso ao banco. Preservar o controle de tentativas ao melhorar esse limite.

## O que falta para colocar no ar

1. Corrigir a falha crítica de URL e a revogação de sessões; acrescentar testes de regressão. Tratar os limites de memória para operação contínua.
2. Validar migrações, mapeamentos, consumo concorrente, idempotência, rollback e backup/restauração em PostgreSQL real. H2 em modo PostgreSQL não comprova compatibilidade completa.
3. Escolher uma forma de executar o backend continuamente: JAR como serviço do sistema ou imagem Docker. O `compose.yaml` atual sobe **somente o PostgreSQL**; não há Dockerfile nem serviço do backend nele.
4. Configurar `SPRING_PROFILES_ACTIVE=postgres`, `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`, `COOKIE_SECURE=true` e `DEMO_DATA=false`. Definir `BOOTSTRAP_PASSWORD` forte no primeiro provisionamento e removê-la depois. A aplicação Java não lê `.env` automaticamente.
5. Ajustar o endereço de escuta. O padrão é `127.0.0.1`; dentro de contêiner ou em várias plataformas será necessário `SERVER_ADDRESS=0.0.0.0`. Na instalação com proxy no mesmo host, loopback pode ser intencional.
6. Configurar domínio, HTTPS, proxy confiável, acesso privado ao banco, segredos e armazenamento persistente.
7. Criar uma verificação de saúde/prontidão e definir reinício automático, logs, monitoramento e alertas. Não há endpoint específico de saúde configurado; é possível usar Actuator ou uma solução simples adequada ao ambiente.
8. Automatizar backup e ensaiar a restauração. O volume Docker persiste dados, mas não substitui backup.
9. Validar navegador/celular: login, navegação, mensagens de erro, assinatura por toque, expiração de sessão e uso entre abas. Incluir testes E2E dos fluxos essenciais.
10. Registrar as alterações no Git e configurar a entrega. O workflow atual valida o build, mas não publica nem instala a aplicação. Há mudanças da refatoração ainda sem commit.

Para uso local, não falta reescrever a aplicação: o servidor iniciou nesta revisão e a página respondeu. Para publicação, a prioridade é corrigir a proteção HTTP e fechar a configuração operacional acima.
